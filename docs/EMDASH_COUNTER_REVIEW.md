# EMDASH_COUNTER_REVIEW.md - EmDash 導入の反証レビュー

- **作成日:** 2026年10月19日
- **目的:** 「WordPress はもう古い。AI化が進んだうちの環境なら EmDash と相性が良い」という導入仮説を、反対の立場から検証する
- **関連:** [EMDASH_RESEARCH.md](./EMDASH_RESEARCH.md)
- **根拠:** EmDash リポジトリ（`main` 88c2fa3、2026年4月〜10月の履歴）、公式ドキュメントのソース、第三者のレビュー記事

---

## 0. 結論

**仮説は「方向性としては正しい。ただ、本番の主力CMSに据えるにはまだ早い」です。**
AI前提のCMSとしての設計は本物です。一方で、**安定版の実績が約3週間しかないこと**、**AIが自律的に書き込む構成ならではのリスク**、**日本語検索の弱さ**の3点は、導入前に手を打っておく必要があります。

判定：**PoC（検証）と、壊れても困らないサイトでの限定導入は「進めてよい」。既存の主要サイトの全面移行は「保留」。**

---

## 1. 前提の訂正：「4月に安定版が一般公開された」は不正確です

リポジトリのバージョン履歴を確認すると、時系列は次のとおりです。

| 日付 | 出来事 |
| --- | --- |
| 2026-04-01 | 一般公開。**v0.1.0（開発者向けプレビュー）** |
| 2026-04〜09 | 0.x 系で約半年、破壊的変更を含む開発が続く（0.42 まで） |
| 2026-09-28 | **v1.0.1 ＝ 実質的な 1.0 安定版**（「これ以降、破壊的変更はメジャーバージョンでのみ行う」と宣言） |
| 2026-10-01〜15 | 1.1 → 1.2 → 1.3 と、2週間でマイナー版を3回リリース |

つまり、4月に公開されたのはプレビュー版です。**後方互換を約束した安定版は、実績がまだ3週間ほどしかありません。**

## 2. 反証ポイント

### 2.1 成熟度：「安定版」の中身はまだ揺れている 〔重大度：高〕

- 約6.5か月で**2,480コミット、コアの変更履歴は751件、DBマイグレーションは93本**あります。開発が速い反面、運用中のサイトはそれだけアップグレードに付き合うことになります。
- 最新の 1.3.1 で直された不具合が象徴的です。Workers のデフォルト設定（`auto` マイグレーション）で、**アップグレード後にページが「中身なし・ステータス200」で配信される**という問題でした。死活監視では検知できない種類の障害です。
- 1.2 では、**ログイン中のユーザー向けに描画したページがキャッシュされ、匿名の訪問者に配信されうる**問題が修正されました（#3898）。情報漏えいにつながる種類の不具合です。
- D1 で、コレクションの**カラム数の上限**に達すると、フィールドの定義だけが残る不具合もありました（#4070）。D1 の物理的な制約は、スキーマ設計にそのまま効いてきます。

→ **対策:** アップグレードは自動にせず、`emdash migrate --check` を通すステージングで検証してから反映します。監視は「ステータス200」ではなく「本文に特定の文字列が含まれるか」を見る合成監視にします。

### 2.2 AI自律運用との相性：相性が良いことが、そのまま攻撃面になる 〔重大度：高〕

「ほとんどの作業がAI化されている」環境ほど、次の連鎖が起きやすくなります。

1. 外部の入力（コメント、インポートしたWordPressのデータ、取り込んだRSSやメール）にプロンプトインジェクションが仕込まれる
2. それを `content_get` や `search` で読み込んだAIエージェントが、指示として解釈してしまう
3. エージェントが持っている `content:write`、`settings:manage`、`schema:write` の権限で、改ざん・公開・削除が実行される

- サイト向けの MCP では、サーバー側がツールの結果を「信頼できないデータ」として扱う仕組みは確認できませんでした。この印（`untrustedContentHint`）が付くのは、実験的なブラウザ API である WebMCP 側だけです。
- MCP で使えるツールは約90個あり、スキーマを含めた `tools/list` はコンテキストを大きく消費します。エージェントがツールを選び間違える余地も増えます。
- 開発元自身も、`destructiveHint` が付いたツールは「呼ぶ前に対象と状態を確認せよ」と注意書きしています。完全自動化と、この確認ステップはぶつかります。

→ **対策（必須）:**
- AI用のアカウントは **Contributor ロール**に限り、スコープは `content:read`、`content:write`、`media:write` だけにします。公開・スキーマ変更・設定変更・サイト移行の権限は人間だけに残します。
- 「AIは下書きまで、公開は人間かCIのゲートが行う」を設計上の原則にします。EmDash は公開済み記事の更新を下書きとして保存するので、この運用は自然に作れます。
- 読み書きのエージェントを分けます。外部入力を読むエージェントには書き込み権限を渡しません。

### 2.3 日本語検索が弱い 〔重大度：中〜高〕

- 全文検索は SQLite の FTS5 を使っていて、**デフォルトのトークナイザは `porter unicode61`** です。これは単語を空白で区切る言語向けで、**日本語の文章は単語に分割されず、部分一致の検索がほぼ効きません。**
- 代わりに `trigram` も選べますが、3文字未満の語（「料金」「解約」など2文字の語）はヒットしません。
- 管理画面には日本語の翻訳（`ja`）があるので、編集の操作面は問題ありません。

→ **対策:** サイト内検索は外部サービス（Algolia、Meilisearch、Cloudflare AI Search など）に任せます。AIエージェントにも `search` に頼らず `content_list` とフィルタで探させます。

### 2.4 Cloudflare ロックイン 〔重大度：中〕

- ライセンスは MIT で、Node.js 版（SQLite / PostgreSQL）もあります。ただ、**中心となる売りのプラグインのサンドボックスは、Workers Paid の Dynamic Workers が前提**です。Node.js 版では `workerd` の子プロセスで代替しますが、ドキュメントもテンプレートも Cloudflare を優先しています。
- WordPress の創設者 Matt Mullenweg は「Cloudflare のサービスを売るための CMS」と批判しています。Search Engine Journal も 1.0 を「Cloudflare ロックイン」という観点で報じました。どちらも利害関係のある立場からの意見なので割り引いて読むべきですが、論点としては妥当です。
- 一方で、サイト全体のエクスポート（`site_export_*`）が標準で用意されているので、データの持ち出し経路はあります。

→ **対策:** PoC の段階で、Node.js と SQLite へのエクスポート・インポートを一度通しておき、移行できることを確認します。

### 2.5 「WordPress は古くなる」も一面的 〔重大度：中〕

- **WordPress 7.0（2026年5月20日リリース）**で、Abilities API と AI Client がコアに入りました。公式の **MCP Adapter** もあります（ただし別プラグインで、まだ 0.x）。WordPress もAIエージェント対応に向けて動いています。
- WordPress には膨大なプラグイン、テーマ、制作会社、人材のエコシステムがあります。SEO、フォーム、EC、会員機能などを即座に用意できる点では、まだ大きな差があります。
- ただし、WordPress の MCP は**プラグイン経由の後付けで、コアには MCP サーバーがありません**。AI Client についても、コスト制御やレート制限がないことや、APIキーの保管方法が批判されています。「最初からAI前提で設計されている」点では EmDash が勝っています。

→ 結論：「WordPress が古くなる」より、**「AIネイティブな新規サイトなら EmDash、エコシステム依存の既存サイトなら WordPress のまま」**という使い分けが妥当です。

### 2.6 開発体制：開発の速さと属人性 〔重大度：低〜中〕

- コミットの約29%が1人のメンテナ（Matt Kane / ascorbic）によるものです。約22%はボット（emdashbot、emdash-autofix）です。コントリビュータは延べ217人いますが、中心メンバーは少数です。
- EmDash 自体がAIエージェントの力を大きく借りて作られています（AI_POLICY.md あり）。開発が速い反面、修正の量も多いです（2.1 参照）。
- 後ろ盾が Cloudflare なので、すぐに放棄される可能性は低いです。ただし、戦略の転換による優先度の変化はありえます。正式な公開ロードマップは「作成中」です。

### 2.7 機能のすき間 〔重大度：中〕

- ファーストパーティのプラグインはまだ 0.x です。SEO（構造化データ、サイトマップの細かい制御）、フォーム、EC、会員機能などは、自作するか外部サービスで補う前提になります。
- 「足りない機能はAIでプラグインを作ればよい」は、うちの環境の強みです。ただし、それは**保守対象のコードを自分で抱える**ことでもあります。

## 3. それでも EmDash を推す理由（反証への反論）

| 論点 | EmDash の優位 |
| --- | --- |
| AI操作の設計 | MCP がコアに組み込み。OAuth 2.1、スコープ × ロール、`_rev` による楽観ロック、編集ロック、下書き → 差分 → 公開のフロー |
| データ構造 | Portable Text なので、AIが生成・変換しやすく、HTMLを壊しにくい |
| 運用負荷 | サーバーレス。Workers 無料プランから始められ、PHP や MySQL のパッチ当てが不要 |
| プラグインの安全性 | 権限を宣言し、隔離環境で実行する（WordPress の脆弱性の大半はプラグイン由来） |
| 開発体験 | TypeScript、型生成、CLI、Agent Skills があり、Claude Code での開発と相性が良い |

## 4. 判定と導入条件

| 用途 | 判定 |
| --- | --- |
| PoC・検証環境 | ✅ すぐ進めてよい |
| 新規の小〜中規模サイト（LP、ブログ、アプリのお知らせ） | ✅ 下記の条件付きで可 |
| 日本語の全文検索が重要なサイト | ⚠️ 外部の検索サービスを併用する前提で可 |
| 既存 WordPress の主要サイトの全面移行 | ⏸ 保留（1.x が3〜6か月安定してから再評価） |
| EC・会員機能・複雑なフォームが中心のサイト | ❌ 現時点では非推奨 |

**導入条件（すべて満たすこと）:**
1. [ ] AIアカウントは最小権限にする（Contributor、`content:*`、`media:write` のみ）。公開は人間かCIのゲートが行う
2. [ ] アップグレードはステージングで `emdash migrate --check` を通してから。本番の `auto` マイグレーションには頼らない
3. [ ] 合成監視で本文の中身まで検査する（ステータス200だけを見ない）
4. [ ] 日本語検索は外部サービスで補う
5. [ ] Node.js へのエクスポートとインポートの移行リハーサルを1回実施する
6. [ ] 外部入力を読むエージェントと、書き込むエージェントを分離する
